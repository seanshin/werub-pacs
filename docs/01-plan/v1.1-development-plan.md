## 2. v1.1 개발 목표

### 핵심 목표
> **실무 투입 가능한 수준의 안정성 확보** — 의료인이 실제 진료에 사용할 수 있도록 뷰어, 관리 화면, 운영 도구를 완성한다.

### 성공 기준

| 기준 | 목표 | 측정 방법 |
|------|------|----------|
| OHIF Viewer 정상 렌더링 | 모든 모달리티 100% | 40개 스터디 전수 검증 |

## 3. 개발 항목 상세

### Sprint 1: OHIF 뷰어 수정 + Admin 배포 (2주)

> 시스템의 존재 이유인 뷰어와 관리 화면을 최우선 정상화

#### S1-1. OHIF Viewer 렌더링 수정 (5일)
**문제**: 특정 스터디에서 검은 화면  
**원인 추정**: Transfer Syntax 디코딩 실패, WADO-RS Bulk Data 이슈, OHIF 빌드 버전

**작업 내용**:
- 브라우저 Console/Network 탭에서 실패 원인 정확히 분석
- OHIF 소스 클론 및 커스텀 빌드 환경 구성
- 최신 OHIF v3.9+ 기반 `openpacs-ohif-kr` 재빌드
  - Cornerstone3D 이미지 디코더 의존성 업데이트
  - 한국어 로케일 적용
  - OpenPACS Report/AI 패널 Extension 통합
- Docker 이미지 빌드 및 배포
- Orthanc 전체 40개 스터디 렌더링 검증 (CT, MR, CR, DX, US, NM 등)

**완료 기준**: Orthanc의 모든 스터디가 OHIF에서 정상 표시

#### S1-2. Admin Dashboard 배포 완료 (3일)
**문제**: `localhost:3002` → 404

**작업 내용**:
- `admin/` Next.js 앱 프로덕션 빌드 (`next build`)
- Dockerfile 작성 및 Docker 이미지 생성
- `docker-compose.yml` admin 서비스 정상 동작 확인
- Nginx 프록시 `/pacs-admin/` → `localhost:3002` 설정
- 페이지별 동작 검증:
  - 판독 워크리스트
  - 배치 정규화 현황
  - AI 모델 관리 / 추론 대시보드
  - 시스템 설정

**완료 기준**: `https://his.example.org/pacs-admin/` 모든 페이지 정상

#### S1-3. Alembic 마이그레이션 전환 (2일)
**문제**: `create_all()` 예외 무시는 운영 위험 (테이블 변경 시 반영 불가)

**작업 내용**:
- 현재 DB 스키마에서 Alembic 초기 마이그레이션 생성 (`alembic revision --autogenerate`)
- `main.py`에서 `create_all()` 제거, Alembic `upgrade head`로 전환
- 향후 스키마 변경 시 마이그레이션 파일로 관리
- 배포 스크립트에 `alembic upgrade head` 통합

**완료 기준**: `alembic upgrade head` 로 스키마 관리, `create_all()` 제거

### Sprint 2: 버그 수정 + 운영 인프라 (1주)

#### S2-1. 한글 Character Set 처리 (1일)
**문제**: Orthanc 로그에 `Specific Character Set (0008,0005) is not supported: 49` 경고

**작업 내용**:
- Orthanc 환경변수 `ORTHANC__DEFAULT_ENCODING: "Utf8"` 확인
- 한국어 DICOM (ISO_IR 149 = EUC-KR) 처리 설정
- 정규화 엔진에서 charset 자동 변환 (ISO_IR 149 → ISO_IR 192) 검증
- 한글 환자명, 검사설명 정상 표시 테스트

**완료 기준**: 한국어 DICOM 데이터 정상 표시 및 검색

#### S2-2. AI 모델 캐시 초기화 수정 (0.5일)
**문제**: 시작 시 `Failed to initialize AI models cache: 'str' object has no attribute 'id'`

**작업 내용**:
- `main.py` lifespan에서 AI 모델 캐시 초기화 코드 수정
- SQLAlchemy ORM 객체 직렬화 불일치 해결

**완료 기준**: 서버 시작 시 에러 없이 캐시 초기화

#### S2-3. 자동 백업 시스템 (1일)
**작업 내용**:
- PostgreSQL 일일 자동 백업 (`pg_dump`) cron 설정
- Orthanc 데이터 볼륨 백업
- 7일 보관 정책 (자동 삭제)
- 복구 절차 문서화 및 실제 복구 테스트

```bash
# 백업 cron
0 3 * * * /home/deploy/openpacs/scripts/backup.sh >> /var/log/openpacs-backup.log 2>&1
```

**산출물**: `scripts/backup.sh`, `scripts/restore.sh`, 복구 절차서

#### S2-4. SSL 인증서 자동 갱신 확인 (0.5일)
**위험**: Let's Encrypt 인증서 만료 시 전체 서비스 다운

**작업 내용**:
- certbot 자동 갱신 cron/systemd timer 확인
- 갱신 테스트 (`certbot renew --dry-run`)
- 만료 30일 전 알림 설정

**완료 기준**: SSL 자동 갱신 동작 확인

#### S2-5. 로그 로테이션 설정 (0.5일)
**위험**: Docker 로그가 디스크를 가득 채울 수 있음

**작업 내용**:
- Docker daemon 로그 드라이버 설정 (`max-size: 50m`, `max-file: 5`)
- 또는 `docker-compose.yml`에 서비스별 로그 제한 추가
- 현재 로그 사이즈 확인 및 정리

**완료 기준**: 각 컨테이너 로그 50MB × 5파일로 제한

#### S2-6. docker-compose.yml 비밀번호 분리 (0.5일)
**위험**: DB 비밀번호가 docker-compose.yml에 하드코딩

**작업 내용**:
- `.env` 파일로 분리 (`DB_PASSWORD`, `ORTHANC_PASSWORD`, `SECRET_KEY`)
- docker-compose.yml에서 `${변수}` 참조로 변경
- `.env`는 `.gitignore`에 추가

**완료 기준**: 비밀번호가 코드에서 제거, `.env`로 관리

### Sprint 3: 판독 워크플로우 + 모니터링 (2주)

#### S3-1. Grafana 모니터링 대시보드 (3일)
**현황**: Prometheus + Grafana 컨테이너 실행 중이나 대시보드 미구성

**작업 내용**:
- FastAPI 메트릭 Exporter 추가 (`prometheus-fastapi-instrumentator`)
- Grafana 대시보드 구성:
  - **시스템**: CPU, Memory, Disk (node-exporter 기반)
  - **API**: 응답 시간 p50/p95/p99, 에러율, RPS
  - **PACS**: 스터디 수, 일일 업로드량, AI 추론 큐 상태
- 알림 규칙 5개:
  - 디스크 사용률 > 90%
  - API 5xx 에러율 > 1%
  - 서비스 다운 (health check 실패)
  - 백업 실패
  - SSL 인증서 만료 30일 전
- UptimeRobot 등록 (외부 가동률 모니터링)

**산출물**: Grafana 대시보드 3종, 알림 규칙 5개, UptimeRobot 설정

**완료 기준**: `https://his.example.org/grafana/`에서 실시간 모니터링 가능

#### S3-2. 판독 워크플로우 완성 (5일)
**작업 내용**:
- 워크리스트 → 뷰어 열기 → 판독 → 리포트 작성 → 서명 → 완료
- 판독 상태 자동 업데이트 (미판독 → 판독중 → 판독완료)
- 긴급 소견 알림 (Critical Finding Notification)
- SOAP 요약 AI 보조 기능 연동
- 감별진단 AI 보조 기능 연동
- OHIF 판독 리포트 패널 연동 (OHIF → OpenPACS Report API)
- AI 분석 버튼 동작 검증 (OHIF Extension → AI Inference API)

**완료 기준**: 워크리스트 → 판독 → 리포트 서명까지 E2E 동작

#### S3-3. 성능 부하 테스트 (2일)
**목적**: 성공 기준 "API p95 < 500ms" 측정 및 검증

**작업 내용**:
- `locust` 또는 `k6`로 부하 테스트 스크립트 작성
- 시나리오: 동시 10명 사용자, 스터디 검색 + 영상 조회 + 리포트 작성
- API 응답 시간 p50/p95/p99 측정
- 병목 지점 분석 및 개선

**완료 기준**: 동시 10명 기준 API p95 < 500ms 달성
