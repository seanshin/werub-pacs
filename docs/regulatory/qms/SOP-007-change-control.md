## 1. 목적

WeRU.B PACS 소프트웨어 의료기기에 대한 모든 변경을 체계적으로 관리하여, 변경으로 인한 위험을 최소화하고 규제 적합성을 유지하기 위한 절차를 규정한다.

## 2. 적용 범위

다음 항목에 대한 변경에 적용한다:
- 소프트웨어 소스코드 (Backend, Viewer, Configuration)
- SOUP 컴포넌트 버전 (Orthanc, OHIF, pydicom 등)
- 인프라 구성 (Docker, Nginx, DB 스키마)
- 문서 (SRS, SDS, 위험관리 문서)
- 배포 환경 설정

## 3. 변경 분류

| 분류 | 기준 | 예시 | 승인 권한 |
|------|------|------|-----------|
| Class I (긴급) | 환자 안전 또는 데이터 무결성 위협 | 보안 취약점 패치 | 개발 책임자 즉시 승인 |
| Class II (주요) | 기능 변경, 새 API, SOUP 업데이트 | 새 모듈 추가, Orthanc 업그레이드 | 변경관리위원회 (CCB) |
| Class III (경미) | UI 개선, 버그 수정, 문서 수정 | 오타 수정, 로그 개선 | 개발 책임자 |

## 4. 변경 절차

### 4.1 변경 요청 (Change Request)
- 변경 요청서 작성 (변경 사유, 영향 범위, 긴급도)
- GitHub Issue로 등록
- 변경 분류 지정

### 4.2 영향 분석 (Impact Analysis)
- 기능 영향: 관련 API endpoints, UI 화면 식별
- 위험 영향: RM-002 위험 분석 재평가 필요 여부
- 규제 영향: 허가 변경 신고 필요 여부 판단
- 호환성 영향: 기존 데이터/인터페이스 호환성

### 4.3 변경 승인
- Class I: 개발 책임자 즉시 승인, 사후 CCB 보고
- Class II: CCB 회의에서 승인/반려/보류 결정
- Class III: 개발 책임자 승인

### 4.4 변경 구현
- Git feature branch 생성
- 코드 변경 및 단위 테스트
- Pull Request 생성 및 코드 리뷰
- 영향받는 문서 갱신

### 4.5 변경 검증
- 변경된 기능 테스트
- 회귀 테스트 (영향받는 모듈)
- 보안 변경 시 취약점 재스캔

### 4.6 변경 릴리스
- main 브랜치 병합
- 버전 태그 부여 (Semantic Versioning)
- 릴리스 노트 작성
- 운영 환경 배포

## 5. 변경 이력 관리

| 기록 항목 | 내용 |
|-----------|------|
| 변경 ID | 고유 식별번호 (CR-YYYY-NNN) |
| 요청일 | 변경 요청 접수일 |
| 요청자 | 변경 요청자 |
| 분류 | Class I / II / III |
| 영향 분석 결과 | 영향받는 모듈, 문서, 위험 |
| 승인자/승인일 | 승인 권한자 및 일자 |
| 구현 완료일 | 변경 구현 및 검증 완료일 |
| 검증 결과 | Pass / Fail / 조건부 승인 |

## 6. SOUP 변경 특별 절차

SOUP (Orthanc, OHIF, pydicom 등) 업데이트 시 추가 활동:
1. 변경 로그(changelog) 검토
2. 보안 패치 내용 확인
3. API 호환성 검증
4. 통합 테스트 전수 수행
5. SBOM (CS-002) 갱신

## 7. 규제 변경 신고 판단 기준

다음 경우 식약처 변경 신고가 필요하다:
- 의도된 사용 목적 변경
- 새로운 위험 발생
- 알고리즘 핵심 로직 변경 (AI 모듈)
- 적용 표준 변경
