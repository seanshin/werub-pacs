## 1. 목적

본 절차서는 WeRU.B PACS 소프트웨어 의료기기의 설계 및 개발 활동을 체계적으로 관리하여 IEC 62304 Class B 요구사항을 충족하고, 식약처(MFDS) 2등급 인허가 요건에 적합한 설계 산출물을 생성하기 위한 절차를 규정한다.

## 2. 적용 범위

- DICOM 서버 (Orthanc 1.12.11 기반)
- WeRU.B Viewer (OHIF v3.12 기반 웹 뷰어)
- FastAPI Backend (340+ API endpoints)
- 지원 인프라 (PostgreSQL, Redis, Celery)

## 3. 용어 정의

| 용어 | 정의 |
|------|------|
| Design Input | 설계 입력 — 사용자 요구사항, 규제 요구사항, 표준 요구사항 |
| Design Output | 설계 출력 — SRS, SDS, Architecture 문서, 소스코드 |
| Design Review | 설계 검토 — 각 Phase 완료 시 수행하는 공식 검토 |
| Design Verification | 설계 검증 — 출력이 입력을 충족하는지 확인 (테스트) |
| Design Validation | 설계 유효성 확인 — 사용자 필요를 충족하는지 확인 |

## 4. 설계 개발 단계

### 4.1 설계 기획 (Design Planning)
- 개발 Phase 정의 (Phase 1~8)
- 각 Phase별 산출물, 검토 기준, 일정 수립
- 위험관리 활동 연계 (RM-001 참조)

### 4.2 설계 입력 (Design Input)
- 사용자 요구사항 수집 (임상의, 방사선사, IT 관리자)
- 규제 요구사항 (의료법, 개인정보보호법, MFDS 허가 기준)
- 기술 요구사항 (DICOM 3.0, DICOMweb, HL7 FHIR)
- 성능 요구사항 (p95 응답시간 < 200ms, 동시 사용자 50명)

### 4.3 설계 출력 (Design Output)
- TD-001 요구사항 명세서 (SRS)
- TD-002 설계 명세서 (SDS)
- TD-003 아키텍처 설계서
- 소스코드 및 Configuration
- TD-005 V&V 보고서

### 4.4 설계 검토 (Design Review)
- 각 Phase 완료 시 설계 검토 회의 수행
- 참석자: 개발 책임자, QA 담당자, 임상 자문
- 검토 결과 기록 및 시정조치 추적

### 4.5 설계 검증 (Design Verification)
- 단위 테스트 (150개 테스트 케이스)
- 통합 테스트 (E2E 31개 로컬 통과)
- 부하 테스트 (p95 = 142ms)
- 보안 테스트 (취약점 스캔 및 패치)

### 4.6 설계 유효성 확인 (Design Validation)
- 사용적합성 평가 (UE-001 참조)
- 임상 환경 시뮬레이션 테스트
- 사용자 수용 테스트 (UAT)

### 4.7 설계 이관 (Design Transfer)
- Docker 기반 배포 패키지
- 운영 환경 배포 절차 (CI/CD)
- 운영자 교육 자료

## 5. 설계 변경 관리

설계 변경 시 SOP-007 변경관리 절차를 따르며, 변경 영향 분석을 수행한 후 적절한 검증/유효성 확인을 재수행한다.
