## 1. 목적

AI 모델의 전체 생명주기(선정 → 통합 → 검증 → 배포 → 모니터링 → 폐기)에 대한 관리 절차를 정의한다. IEC 62304 소프트웨어 생명주기 프로세스 및 ISO 14971 위험관리 원칙에 따라, WeRU.B PACS에 통합되는 모든 AI 모델의 안전성과 유효성을 보장하기 위한 체계적인 관리 프로세스를 수립한다.

## 2. 적용 범위

본 절차서는 다음 범위에 적용된다:

- WeRU.B PACS에 통합된 **29개 AI 모델** (의료 13종, 범용 LLM 16종)
- **WeRU.B AI Server v2.50.0** (RTX 5080 16GB, ONNX Runtime)
- **5개 AI 파이프라인**: medical, chest-xray, ct-abdomen, emergency-triage, consensus
- AI 모델의 선정, 도입, 통합, 검증, 배포, 운영 모니터링, 변경, 비활성화 및 폐기에 이르는 전 과정
- AI 추론 결과의 DICOM 표준 형식(SR/SC/SEG/ANN) 저장 및 표시

## 4. 모델 선정 및 도입 절차

### 4.1 후보 모델 평가 기준

AI 모델 도입 시 다음 항목을 평가한다:

| 평가 항목 | 최소 기준 | 평가 방법 |
|-----------|-----------|-----------|
| 정확도 (Accuracy) | ≥ 85% | 벤치마크 테스트 세트 |
| 민감도 (Sensitivity) | ≥ 80% | 양성 검출률 |
| 특이도 (Specificity) | ≥ 85% | 음성 배제률 |
| AUC-ROC | ≥ 0.85 | ROC 곡선 분석 |
| 추론 시간 | ≤ 30초/건 (GPU), ≤ 120초/건 (CPU) | 평균 처리 시간 |
| 라이선스 | 상용/오픈소스 허용 | 법률 검토 |
| 학습 데이터 | 출처/편향 확인 | 데이터시트 검토 |
| 재현성 | 동일 입력 → 동일 출력 | 반복 실행 검증 |
| DICOM 호환성 | SR/SC/SEG 출력 | 출력 형식 검증 |

### 4.2 벤치마크 테스트

- **최소 테스트 세트**: 100건 이상 (모달리티별, 정상/비정상 균형 포함)
- **골드 스탠다드**: 2인 이상 전문의 합의 판독 결과
- **테스트 환경**: 운영 환경과 동일한 하드웨어/소프트웨어 구성
- **결과 기록**: 혼동 행렬(Confusion Matrix), ROC 곡선, PR 곡선 산출
- **통계 분석**: 95% 신뢰구간, McNemar 검정 (기존 모델 대비)

### 4.3 도입 승인 프로세스

```
[후보 모델 식별] → [기술 검토] → [벤치마크 테스트] → [위험 평가] → [승인 심의] → [등록]
```

1. **기술 검토**: 개발팀이 모델 아키텍처, 학습 데이터, 라이선스를 검토
2. **벤치마크 테스트**: 4.2절 기준에 따라 성능 검증 수행
3. **위험 평가**: ISO 14971에 따른 위험 분석 (RM-002 R-013~R-016 참조)
   - 위양성(False Positive): 불필요한 추가 검사 유발 위험
   - 위음성(False Negative): 병변 미검출로 인한 진단 지연 위험
   - 모델 편향(Bias): 특정 인구집단에 대한 성능 편차
4. **승인 심의**: 품질관리 책임자 + 임상 자문의 합동 심의
5. **등록**: Orchestration Platform에 모델 ID, 버전, 체크섬 등록

### 4.4 도입 산출물

| 산출물 | 책임자 | 보존 기간 |
|--------|--------|-----------|
| 모델 평가 보고서 | 개발팀 | 5년 |
| 벤치마크 테스트 결과서 | QA팀 | 5년 |
| 위험 평가 결과서 | 품질관리 책임자 | 제품 수명주기 + 5년 |
| 도입 승인서 | 품질관리 책임자 | 제품 수명주기 + 5년 |

## 5. 모델 통합 및 배포

### 5.1 Orchestration Platform 등록

AI 모델은 WeRU.B PACS Orchestration Platform을 통해 관리된다:

- **파이프라인 CRUD**: 파이프라인 생성, 조회, 수정, 삭제
- **모델 등록**: 모델 ID, 버전, 엔드포인트, 파라미터 설정
- **프로덕션 승격**: 스테이징 → 프로덕션 승격 절차 (승인 필수)
- **파이프라인 구성**: 단일 모델 또는 다중 모델 앙상블 구성

### 5.2 모델 버전 관리

| 관리 항목 | 형식 | 예시 |
|-----------|------|------|
| 모델 ID | `{vendor}-{name}-{version}` | `werub-medical-v2.3.1` |
| 모델 버전 | Semantic Versioning | `2.3.1` |
| 체크섬 | SHA-256 | `a3f2b1c...` |
| 가중치 파일 | 버전별 보관 | `/models/werub-medical/v2.3.1/weights.onnx` |
| 설정 파일 | Git 관리 | `config/model-configs/{model-id}.yaml` |

- 모든 모델 파일은 SHA-256 체크섬으로 무결성을 검증한다
- 이전 버전은 롤백을 위해 최소 2개 버전을 보관한다
- 버전 변경 이력은 변경관리 시스템에 기록한다 (SOP-007 참조)

### 5.3 A/B 비교 테스트

신규 모델 또는 업데이트된 모델 배포 전 A/B 비교 테스트를 수행한다:

1. **테스트 설계**: 동일 데이터셋에 대해 기존 모델(A)과 신규 모델(B) 동시 실행
2. **비교 항목**: 정확도, 민감도, 특이도, 추론 시간, 리소스 사용량
3. **통계 검정**: McNemar 검정 또는 DeLong 검정으로 유의미한 차이 확인
4. **판정 기준**: 신규 모델이 기존 대비 열등하지 않음을 입증 (Non-inferiority)
5. **기록**: A/B 테스트 결과 보고서 작성 및 보관

### 5.4 배포 절차

```
[A/B 테스트 완료] → [배포 승인] → [스테이징 배포] → [검증] → [프로덕션 승격] → [모니터링]
```

1. 스테이징 환경에서 최소 24시간 안정성 검증
2. 프로덕션 승격 시 품질관리 책임자 승인 필수
3. 배포 후 72시간 집중 모니터링 수행

### 5.5 롤백 절차

다음 상황 발생 시 즉시 롤백을 수행한다:

| 롤백 조건 | 조치 | 시간 목표 |
|-----------|------|-----------|
| 추론 오류율 > 5% | 이전 버전으로 자동 롤백 | 5분 이내 |
| 민감도 급격 저하 (> 10%p) | 모델 비활성화 + 이전 버전 복원 | 15분 이내 |
| GPU 메모리 초과 (OOM) | 해당 모델 비활성화 | 즉시 |
| 보안 취약점 발견 | 긴급 비활성화 + CAPA 개시 | 즉시 |

- 롤백 시 이전 버전의 체크섬 재검증 필수
- 롤백 사유 및 조치 내용을 변경관리 시스템에 기록 (SOP-007 참조)

## 6. AI 결과 표시 원칙

### 6.1 표시 요구사항

모든 AI 추론 결과는 다음 사항을 준수하여 표시한다:

| 표시 항목 | 내용 | 필수 여부 |
|-----------|------|-----------|
| AI 보조 경고문 | "AI 보조 참고용 - 의사의 최종 판단이 필요합니다" | 필수 |
| 신뢰도 점수 | Confidence Score (0~100%) 수치 표시 | 필수 |
| 모델 정보 | 모델 ID, 버전, 파이프라인 명칭 | 필수 |
| 분석 일시 | 추론 수행 시각 (ISO 8601) | 필수 |
| 제한 사항 | 모델의 알려진 제한 사항 | 권장 |

### 6.2 신뢰도 기반 표시 등급

| 신뢰도 범위 | 표시 등급 | UI 표시 | 임상 조치 |
|-------------|-----------|---------|-----------|
| ≥ 90% | 높음 | 녹색 배지 | 참고 활용 가능 |
| 70~89% | 보통 | 황색 배지 | 주의 필요, 추가 검토 권장 |
| < 70% | 낮음 | 적색 배지 | 참고만 가능, 독립 판독 필수 |

### 6.3 DICOM 표준 저장 형식

AI 추론 결과는 DICOM 표준 형식으로 저장한다:

| 결과 유형 | DICOM IOD | 용도 |
|-----------|-----------|------|
| 구조화 보고서 | SR (Structured Report) | 소견, 측정값, 진단 코드 |
| 주석 영상 | SC (Secondary Capture) | 히트맵, 바운딩 박스 오버레이 |
| 분할 영상 | SEG (Segmentation) | 장기/병변 분할 마스크 |
| 주석 | ANN (Annotation) | 포인트, 폴리곤 등 벡터 주석 |

- 모든 AI 생성 DICOM 객체에는 AI 모델 정보를 Private Tag 또는 Contributing Equipment Sequence에 기록
- Series Description에 "[AI]" 접두사를 포함하여 AI 생성물임을 명시

## 7. 성능 모니터링

### 7.1 모니터링 KPI

| KPI | 산출 주기 | 최소 기준 | 측정 방법 |
|-----|-----------|-----------|-----------|
| 정확도 (Accuracy) | 월간 | ≥ 85% | 전문의 판독과 비교 |
| 민감도 (Sensitivity) | 월간 | ≥ 80% | 양성 케이스 검출률 |
| 특이도 (Specificity) | 월간 | ≥ 85% | 음성 케이스 배제율 |
| 위양성률 (FPR) | 월간 | ≤ 15% | 1 - 특이도 |
| 위음성률 (FNR) | 월간 | ≤ 20% | 1 - 민감도 |
| 평균 추론 시간 | 일간 | ≤ 30초 (GPU) | 서버 로그 |
| 추론 성공률 | 일간 | ≥ 99% | 오류 로그 |

### 7.2 GPU 모니터링

WeRU.B AI Server의 GPU 리소스를 실시간 모니터링한다:

| 모니터링 항목 | 임계값 | 알림 |
|---------------|--------|------|
| VRAM 사용률 | > 90% | Warning 알림 |
| GPU 사용률 | > 95% (지속 5분) | Warning 알림 |
| 모델별 처리량 | < 기준의 50% | Critical 알림 |
| 추론 큐 대기 수 | > 50건 | Warning 알림 |
| GPU 온도 | > 85°C | Critical 알림 |

- GPU 모니터링 데이터는 스케줄러가 주기적으로 수집 (1분 간격)
- 27개 모델의 VRAM 할당 현황을 대시보드에 표시
- 리소스 부족 시 우선순위 기반 모델 스케줄링 적용

### 7.3 성능 임계값 및 조치

| 조건 | 조치 | 책임자 |
|------|------|--------|
| 민감도 < 80% (단일 월) | 원인 조사 + 데이터 검토 | 개발팀 |
| 민감도 < 80% (연속 2개월) | 모델 비활성화 검토 | 품질관리 책임자 |
| 민감도 < 70% | 즉시 비활성화 + CAPA 개시 | 품질관리 책임자 |
| 위음성률 > 25% | 모델 비활성화 + 원인 분석 | 품질관리 책임자 |
| 추론 시간 > 60초 (평균) | 최적화 또는 하드웨어 증설 검토 | 개발팀 |

### 7.4 드리프트 감지

모델 성능 드리프트(Model Drift)를 체계적으로 감지한다:

- **데이터 드리프트**: 입력 데이터 분포 변화 모니터링 (KL Divergence, PSI)
- **개념 드리프트**: 예측 정확도 추세 분석 (CUSUM, Page-Hinkley 검정)
- **월간 성능 비교**: 이전 3개월 평균 대비 현재 월 성능 비교
- **통계적 유의성 검정**: p-value < 0.05 시 드리프트 발생으로 판정
- **드리프트 발생 시**: CAPA 절차 개시 (SOP-008 참조), 재학습 또는 모델 교체 검토

## 8. 모델 변경 관리

### 8.1 변경 분류

| 분류 | 정의 | 예시 | 승인 수준 | 재검증 범위 |
|------|------|------|-----------|-------------|
| Minor | 파라미터/설정 조정 | 추론 임계값 변경, 전/후처리 파라미터 수정 | 개발팀장 | 회귀 테스트 |
| Major | 모델 아키텍처 변경 | 모델 구조 수정, 새로운 출력 형식 | 품질관리 책임자 | 전체 벤치마크 재수행 |
| Critical | 학습 데이터 변경 | 재학습, 전이학습, 파인튜닝 | 품질관리 책임자 + 임상 자문의 | 전체 검증 + 임상 평가 |

### 8.2 변경 절차 (SOP-007 연계)

1. **변경 요청서 작성**: 변경 사유, 범위, 영향 분석 포함
2. **영향 분석**: 해당 모델을 사용하는 파이프라인, 연관 모델 식별
3. **위험 평가 갱신**: ISO 14971에 따른 잔여 위험 재평가
4. **재검증**: 변경 분류에 따른 범위의 검증 수행
5. **배포 승인**: 5.4절 배포 절차 준수
6. **문서 갱신**: 모델 카드, SBOM, 위험 분석서 갱신

### 8.3 재학습 관리

모델 재학습 시 다음 사항을 준수한다:

- **데이터셋 분리**: 학습(Training) / 검증(Validation) / 테스트(Test) 데이터셋 엄격 분리
  - 학습: 70%, 검증: 15%, 테스트: 15% (최소 비율)
  - 테스트 데이터셋은 학습 과정에서 절대 노출 금지
- **데이터 품질**: 학습 데이터의 라벨링 정확도, 편향, 대표성 검증
- **비교 검증**: 재학습 전/후 모델 성능을 동일 테스트 세트로 비교
- **가중치 관리**: 재학습 전 가중치 백업, 체크섬 기록

## 9. 모델 비활성화/폐기

### 9.1 비활성화 절차

| 비활성화 사유 | 절차 | 소요 시간 |
|---------------|------|-----------|
| 성능 저하 (7.3절 기준) | 관리 콘솔에서 토글 OFF → 기록 | 즉시 |
| 보안 취약점 발견 | 긴급 비활성화 → CAPA 개시 → 기록 | 즉시 |
| 상위 모델 대체 | A/B 테스트 완료 → 구모델 비활성화 → 기록 | 계획적 |
| 라이선스 만료/변경 | 법률 검토 → 비활성화 → 대체 모델 검토 | 계획적 |

- 비활성화 시 해당 모델이 포함된 파이프라인의 동작 확인 필수
- 파이프라인에서 비활성화된 모델은 자동 스킵 또는 대체 모델로 전환

### 9.2 폐기 절차

1. 비활성화 상태에서 최소 30일 경과 후 폐기 검토
2. 해당 모델의 추론 결과 보존 확인 (의료법 5년 보존)
3. 모델 가중치 파일 아카이브 (오프라인 백업)
4. Orchestration Platform에서 모델 등록 해제
5. 폐기 기록 작성 및 보존 (**최소 5년**)

### 9.3 폐기 기록 항목

| 기록 항목 | 내용 |
|-----------|------|
| 모델 ID/버전 | 폐기 대상 모델 식별 정보 |
| 도입일 | 최초 프로덕션 배포일 |
| 폐기일 | 실제 폐기 수행일 |
| 폐기 사유 | 성능 저하 / 대체 / 보안 / 라이선스 등 |
| 누적 추론 건수 | 도입~폐기 기간 총 추론 수행 건수 |

### 10.2 SOUP 관리 활동

- **버전 고정**: `requirements.txt`, `Dockerfile`에 정확한 버전 명시
- **보안 취약점 모니터링**: CVE 데이터베이스, Dependabot, Snyk를 통한 주기적 스캔
- **호환성 검증**: SOUP 업데이트 시 모든 AI 모델에 대한 회귀 테스트 수행
- **라이선스 준수**: SBOM(CS-002)에 전체 의존성 기록, 라이선스 충돌 검토
- **업데이트 주기**: 보안 패치는 즉시, 기능 업데이트는 분기별 검토

### 10.3 SOUP 변경 시 영향 평가

SOUP 버전 변경 시 다음 사항을 평가한다:

1. API 호환성 (Breaking Changes 확인)
2. 모델 추론 결과의 일관성 (동일 입력 → 동일 출력)
3. 성능 영향 (추론 시간, 메모리 사용량)
4. 보안 영향 (신규 취약점, 패치된 취약점)

## 11. 위험 관리 연계

### 11.1 AI 관련 위험 항목 (RM-002 참조)

| 위험 ID | 위험 항목 | 심각도 | 발생 확률 | 위험 수준 | 경감 조치 |
|---------|-----------|--------|-----------|-----------|-----------|
| R-013 | AI 위양성 (False Positive) | 중 | 중 | 허용 가능 | 신뢰도 표시 + 의사 확인 의무화 |
| R-014 | AI 위음성 (False Negative) | 고 | 저 | ALARP | 민감도 모니터링 + 80% 미만 시 비활성화 |
| R-015 | AI 모델 드리프트 | 중 | 중 | 허용 가능 | 월간 성능 비교 + CUSUM 검정 |
| R-016 | AI 서버 장애 | 중 | 저 | 허용 가능 | 폴백 경로(수동 판독) + 99.5% 가용성 |

### 11.2 AI 위양성/위음성 대응 절차

**위양성 대응:**
1. 의사가 AI 판독 결과와 불일치 시 "AI 결과 기각" 기록
2. 기각 사유를 데이터베이스에 저장
3. 월간 위양성 통계 집계 및 추세 분석
4. 위양성률 > 15% 시 원인 분석 및 모델 재교정 검토

**위음성 대응:**
1. AI가 미검출한 병변을 의사가 발견 시 "AI 미검출" 기록
2. 해당 케이스를 재학습 후보 데이터셋에 추가 (비식별화 후)
3. 위음성률 > 20% 시 CAPA 절차 개시 (SOP-008 참조)
4. 임상적으로 중대한 위음성(악성 종양 등) 발생 시 즉시 보고

### 11.3 CAPA 연계

모델 성능 이상 또는 드리프트 감지 시 SOP-008 CAPA 절차에 따라 처리한다:

- **시정 조치(Corrective Action)**: 즉시 모델 비활성화, 원인 분석, 재교정/교체
- **예방 조치(Preventive Action)**: 모니터링 강화, 드리프트 감지 임계값 조정, 재학습 주기 단축

### 12.1 식약처 SaMD 가이드라인 준수

본 절차서는 다음 규제 요건을 준수한다:

| 규제/가이드라인 | 적용 사항 |
|----------------|-----------|

| 식약처 AI 기반 SaMD 허가 심사 가이드라인 | 모델 성능 검증, 변경관리 |

| IEC 82304-1:2016 | 건강 소프트웨어 일반 요구사항 |
| IMDRF SaMD 프레임워크 | SaMD 분류 및 임상 평가 |

### 12.2 임상용/연구용 AI 모델 분리

| 구분 | 정의 | 관리 수준 | 표시 |
|------|------|-----------|------|
| 임상용 (Clinical) | 환자 진료에 직접 활용 | 전체 검증 + 규제 승인 | "AI 보조 판독" |
| 연구용 (Research) | 연구/교육 목적 전용 | 내부 벤치마크 | "연구용 - 임상 사용 불가" |

- 임상용 모델만 프로덕션 파이프라인에 등록 가능
- 연구용 모델은 별도 환경에서만 실행, 환자 데이터 접근 시 비식별화 필수
- 연구용 → 임상용 전환 시 전체 도입 절차(4절) 재수행

### 12.3 AI 모델 변경 시 변경허가/변경신고 판단 기준

| 변경 유형 | 판단 기준 | 규제 조치 |
|-----------|-----------|-----------|
| 신규 AI 모델 추가 | 기존 허가 범위 외 새로운 임상 용도 | 변경허가 |
| 기존 모델 업데이트 (동일 용도) | 성능 동등 이상, 출력 형식 동일 | 변경신고 |
| 파라미터 미세 조정 | 임상 성능에 유의미한 변화 없음 | 사내 기록 |
| AI 프레임워크 변경 (SOUP) | 출력 동등성 검증 완료 | 변경신고 |
| 학습 데이터 변경 (재학습) | 대상 질환/인구집단 변경 여부에 따라 | 변경허가 또는 변경신고 |

- 변경허가/변경신고 해당 여부는 품질관리 책임자와 RA(규제 담당자)가 합동 판단
- 판단 근거를 문서화하고 변경관리 기록에 포함
