# CS-001 사이버보안 계획서 (Cybersecurity Plan)

| 항목 | 내용 |
|------|------|
| 문서 ID | CS-001 |
| 버전 | 2.0 |
| 작성일 | 2026-05-18 |
| 상태 | 승인 |
| 적용 표준 | 식약처 의료기기 사이버보안 허가심사 가이드라인 (2023) |
| 제품명 | WeRU.B PACS |
| 등급 | 2등급 의료기기 |

## 1. 목적

WeRU.B PACS 소프트웨어 의료기기의 사이버보안 위협을 식별하고, 보안 설계/구현/유지 전략을 정의하여 환자 데이터 보호 및 시스템 안전성을 확보한다.

## 2. STRIDE 위협 모델 — 컴포넌트별 상세 분석

### 2.1 Nginx (Reverse Proxy / TLS Termination)

| 위협 유형 | 시나리오 | S | P | Risk | 대응 |
|-----------|----------|---|---|------|------|
| Spoofing | 가짜 인증서로 중간자 공격 | S4 | P2 | M | Let's Encrypt 자동 갱신, HSTS 헤더 |
| Tampering | HTTP 응답 변조 | S3 | P1 | L | TLS 1.3 종단간 암호화 |
| Info Disclosure | 서버 버전 노출 | S2 | P4 | M | `server_tokens off`, 커스텀 에러 페이지 |
| DoS | DDoS / Slowloris | S3 | P3 | M | Rate Limiting, connection timeout, fail2ban |

### 2.2 FastAPI Backend (8001)

| 위협 유형 | 시나리오 | S | P | Risk | 대응 |
|-----------|----------|---|---|------|------|
| Spoofing | JWT 토큰 위조 | S4 | P2 | M | HS256 서명 검증, 비밀키 환경변수 관리 |
| Tampering | API 요청 데이터 변조 | S3 | P2 | L | 입력 검증 (Pydantic), TLS |
| Repudiation | API 호출 부인 | S3 | P2 | L | AuditMiddleware 전체 기록 |
| Info Disclosure | 에러 스택트레이스 노출 | S2 | P3 | L | production 모드 에러 핸들링 |
| DoS | 대량 API 호출 | S3 | P3 | M | RateLimitMiddleware (100 req/min) |
| EoP | RBAC 우회 | S4 | P2 | M | 엔드포인트별 역할 검증 데코레이터 |

### 2.3 Orthanc (DICOM Server — 8042/4242)

| 위협 유형 | 시나리오 | S | P | Risk | 대응 |
|-----------|----------|---|---|------|------|
| Spoofing | 위장 AE Title로 DICOM 전송 | S3 | P2 | L | AE Title 화이트리스트, DicomCheckCalledAet |
| Tampering | DICOM 데이터 위변조 | S4 | P2 | M | 감사 로그, pgcrypto 무결성 검증 |
| Info Disclosure | Orthanc Explorer 무단 접근 | S4 | P2 | M | Basic Auth, Nginx 프록시 뒤에 배치 |
| DoS | 대량 DICOM C-STORE 공격 | S3 | P2 | L | 연결 제한, 스토리지 모니터링 |

### 2.4 PostgreSQL (5432)

| 위협 유형 | 시나리오 | S | P | Risk | 대응 |
|-----------|----------|---|---|------|------|
| Spoofing | DB 접근 자격 탈취 | S4 | P2 | M | 127.0.0.1 바인딩, 전용 사용자, 강력한 비밀번호 |
| Tampering | 직접 SQL로 데이터 변조 | S4 | P1 | L | 최소 권한 원칙, WAL, 감사 |
| Info Disclosure | DB 덤프 유출 | S4 | P1 | L | 암호화 백업(AES-256), 접근 통제 |

### 2.5 Redis (6379)

| 위협 유형 | 시나리오 | S | P | Risk | 대응 |
|-----------|----------|---|---|------|------|
| Info Disclosure | 세션 데이터 유출 | S3 | P2 | L | 127.0.0.1 바인딩, Docker 내부 네트워크 |
| DoS | 메모리 과다 사용 | S2 | P3 | L | maxmemory 설정, eviction 정책 |

### 2.6 WeRU.B Viewer (OHIF / 3001)

| 위협 유형 | 시나리오 | S | P | Risk | 대응 |
|-----------|----------|---|---|------|------|
| Tampering | XSS로 뷰어 UI 변조 | S3 | P2 | L | CSP 헤더, sanitize 입력 |
| Info Disclosure | 브라우저 캐시에 DICOM 잔류 | S3 | P3 | M | Cache-Control: no-store (민감 데이터) |

### 4.2 권한 검증 구현

- FastAPI `Depends()` 데코레이터로 각 엔드포인트에 역할 검증

## 5. 인증 및 세션 보안

| 항목 | 구현 |
|------|------|
| 인증 방식 | JWT (Access Token 1시간, Refresh Token 7일) |
| 서명 알고리즘 | HS256 |
| 비밀번호 해싱 | bcrypt (cost factor 12) |
| 계정 잠금 | 5회 연속 실패 시 30분 잠금 |
| 동시 세션 | 최대 3개 (초과 시 가장 오래된 세션 만료) |
| IP 기록 | 모든 세션에 접속 IP 기록 |
| Refresh Token | 일회용 (사용 시 새 토큰 발급, 이전 무효화) |

## 6. 데이터 보안

### 6.1 암호화

| 데이터 상태 | 방법 | 상세 |
|------------|------|------|
| 전송 중 (in transit) | TLS 1.3 | Let's Encrypt, HSTS, OCSP Stapling |
| 저장 시 (at rest) — 민감 필드 | pgcrypto | 환자 민감정보 필드 |
| 저장 시 — 백업 | AES-256 | 일일 백업 암호화 |
| 비밀번호 | bcrypt | cost factor 12, salt 자동 |

### 6.2 개인정보 보호

| 조치 | 구현 |
|------|------|
| 익명화 | QC 모듈 — DICOM 태그에서 개인정보 제거 (연구용) |
| 최소 수집 | 의료 목적 필수 정보만 저장 |
| 접근 제한 | RBAC — 역할별 데이터 접근 범위 제한 |
| 감사 추적 | 모든 환자 데이터 접근 기록 (audit_logs) |
| 동의 | 의료기관의 환자 동의 절차에 위임 |

## 7. 감사 및 모니터링

### 7.1 자동 감사 로그

- `AuditMiddleware`가 모든 API 호출을 자동 기록
- 기록 항목: 사용자, IP, 시간, HTTP 메서드, 경로, 상태 코드, 리소스 ID
- `audit_logs` 테이블에 JSONB 형식 저장
- **삭제 불가** (admin 역할도 DELETE 권한 없음)

### 7.2 보안 이벤트 감지

| 이벤트 | 감지 방법 | 알림 |
|--------|-----------|------|
| 로그인 5회 실패 | login_attempts 카운터 | 계정 잠금 + 로그 기록 |
| 비정상 대량 조회 | Rate Limit 초과 | 429 응답 + 로그 기록 |
| 권한 위반 접근 | RBAC 검증 실패 | 403 응답 + 로그 기록 |
| 연속 401 응답 | 토큰 만료/위조 | 로그 기록 |

## 9. 인시던트 대응 플레이북

### 9.1 대응 절차 개요

```
탐지(Detection) → 분류(Triage) → 격리(Containment)
    → 분석(Analysis) → 복구(Recovery) → 보고(Reporting) → 개선(Improvement)
```

### 9.2 상세 플레이북

| 단계 | 활동 | 담당 | 기한 | 상세 |
|------|------|------|------|------|
| 1. 탐지 | 감사 로그/모니터링 이상 감지 | IT 관리자 | 즉시 | 자동 알림 또는 수동 발견 |
| 2. 분류 | 심각도 판정 (Critical/High/Medium/Low) | 보안담당자 | 30분 내 | 영향 범위, 데이터 유출 여부, 환자 안전 영향 |
| 3. 격리 | 영향 시스템 네트워크 분리 | IT 관리자 | 1시간 내 | Docker 컨테이너 중지, 방화벽 차단, 계정 잠금 |
| 4. 증거 수집 | 로그 보존, 스냅샷 생성 | IT 관리자 | 격리 후 즉시 | audit_logs, Nginx 로그, Docker 로그 |
| 5. 분석 | 침해 범위/원인 분석 | 개발팀 + 보안 | 24시간 내 | 코드 리뷰, 로그 분석, IOC 식별 |
| 6. 복구 | 시스템 복원, 패치 적용 | 개발팀 | 72시간 내 | 백업 복원, 취약점 패치, 비밀번호 초기화 |
| 7. 보고 | 규제기관/고객 보고 | QA + RA | 72시간 내 | 식약처(해당 시), 개인정보위(해당 시), 고객 |
| 8. 개선 | CAPA 수행 | QA | 30일 내 | SOP-008, 재발 방지 조치, 절차 개선 |

### 9.3 시나리오별 대응

| 시나리오 | 즉시 조치 | 후속 조치 |
|----------|-----------|-----------|
| 환자 데이터 유출 | 해당 서비스 중단, 접근 차단 | 유출 범위 파악, 개인정보위 신고(72h), 영향 환자 통지 |
| 랜섬웨어 | 네트워크 분리, 컨테이너 중지 | 백업에서 복원, 감염 경로 분석 |
| DDoS 공격 | Nginx rate limit 강화, IP 차단 | CDN 도입 검토, 방화벽 정책 강화 |
| 내부자 위협 | 해당 계정 잠금 | 감사 로그 분석, 접근 범위 확인, 법적 조치 |
